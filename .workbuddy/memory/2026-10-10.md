## 本次改动（用户要求：不要改其他代码，只改 style.css）
文件：仅 `style.css`，三个规则。

1. **`.hero__panel` 收窄 + 收紧**

   - `padding: 26px 30px 24px → 22px 26px 20px`
2. **`.hero__content` 下边距减小**（flex `align-items: flex-end`，下边距越小卡片越靠下）
   - `padding-block: calc(var(--nav-h) + 20px) clamp(30px, 7vh, 78px)`

3. **`.hero__title` 字号上限下调**（收窄的连带修正）
   - `clamp(30px, 4.6vw, 58px) → clamp(30px, 4.2vw, 50px)`

## 关键定位结论（值得记住）
- **遮挡病根不是高度，是宽度**：卡片 `width:100%; max-width:620px` 从左侧栅格起算，
  右边缘落在 x=727px，**正好越过画面中线**（x=723px 是 `.compare__handle` 中心），
  把 52px 直径的滑块整宽盖住。**只把卡片变矮完全没用**（之前误判过一次）。
- 参数扫描（1440×900 实测右边缘）：
  | max-width | panel right | handle 中心 | overlap | 卡片高 |
  |---|---|---|---|---|
  | 620px | 727 | 723 | **true（压 52×47）** | 346 |
  | 540px | 647 | 723 | false | 412 |
  | 470px | 577 | 723 | false | 441 |
  - 「收窄反而变高」是反直觉的正确现象：窄了会让文字折行变高，反而脱离
    `clamp(30px,7vh,78px)` 的下边距挤压区，所以 500/470 稳定在 441px、540 是 412px。
- **标题单行上界 = 52px**（卡片宽 540px、内容宽 486px 时）。58px 会折成两行，
  故取 50px 留余量。

## 验证（改动后 6 种桌面尺寸全部通过）

# 2026-10-10（追加）— GALLERY 窄屏卡片溢出修复

> 用户诉求：窄屏下 GALLERY 卡片宽于屏幕，内部图片显示不全、横向滑动异常；
> 要求只修这里，不动其他。

## 病根：百分比 flex-basis 撞上 max-content（循环基准）
`@media (max-width:620px)` 里写的是 `.card-shot { flex: 0 0 84%; }`。
问题是父级 `.gallery__list` 是 `width: max-content`，而卡片又是它的 flex 子项：
**84% 的解析基准反过来又取决于内容宽度**，两边互相牵制，直接算爆。

实测（真实 `index.html`，加探针注入）：
| 视口 | 卡片宽 | viewport clientW | scrollW | 能否滑动 |
|---|---|---|---|---|
| 588 | **2867** | 552 | 14417 | 卡片 5 倍于屏幕 |
| 528 | **2867** | 492 | 14417 | 同上 |
| 510 | **2867** | 474 | 14417 | 同上 |
- `viewportRightOverflow=false`、`bodyOverflowX=false` 会**骗人**：因为撑爆的是
  滚动容器内部，页面本身没横向溢出，所以只查 body 溢出根本发现不了。
- 修复前 scrollPages 达 26~30 页；修复后 3.6 页。

## 修复：一行，给死上限
```css
/* style.css ~L488（@media max-width:620px 内） */
.card-shot { flex: 0 0 clamp(260px, 80vw, 340px); }   /* 原：flex: 0 0 84% */
```
用 `clamp(260px, 80vw, 340px)`：最大 340px，哪怕 `max-content` 再被撑爆也不连锁放大；
最小 260px 保证小屏不至于窄到看不清；80vw 让中间区段（约 425px 以上视口）留出
~20% 露出下一张卡，形成"还有更多"的滑动暗示。

三种候选实测对比（620/560/430 视口）：
| 方案 | 卡片宽 | 结论 |
|---|---|---|
| A `84%` | 460 / 410 / 395 | 超出 clientW（552/492/474），BUST |
| B `calc(100vw - 74px)` | 514 / 454 / 436 | 同样超出，BUST |
| C `clamp(260px, 80vw, 340px)` | 340 / 340 / 340 | 全部 fits，**采用** |
- 注意「卡片宽 460 vs clientW 552」在模拟页里看着像 OK（460<552），是因为模拟页
  list 反被压小了；真实页面才会出现 2867 这种爆值。**必须拿真实页验证**。

## 验证结论（修后真实 index.html 扫 14 档视口）
1440 / 1100 / 900 / 860 / 800 / 700 / 660 / 620 / 580 / 560 / 480 / 430 / 390 / 360：
- 全部 `cardFitsViewport=true`，`viewportRightOverflow=false`，`bodyOverflowX=false`
- 卡片宽随档位：366（>860）→ 272（620–860）→ 340（≤600），单调、无跳变
- 截图 560 / 430 / 390 目视确认：卡片完整落在视口内，前后两半图都完整，
  右侧露出下一张卡，横向滑动正常

## 箭头/滚动验证（隔离出 `_galonly.html` 单独跑，只加载真实 style.css + script.js）
- 点击逻辑本身正确；**无头下 `behavior:'smooth'` 的 scrollBy 不会推进**
  （`scrollLeft` 卡在 2 不动），把 smooth 劫持成 instant 后：
  `nextMoved=true`，`start:2 → n1:362 → end:1292(max) → back:1292`，终点可达 max。
- `El.prototype.scrollBy` 劫持 + `setTimeout` 分步点击，是无头测横向滚动的可用套路。
- 结论：箭头按钮与滚动容器在修复后完全正常，之前的 false 只是测量环境假象。
